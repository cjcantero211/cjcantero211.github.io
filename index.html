Cybersecurity case study
SQL Injection (SQLi): what it is, how it happens, and how to prevent it.

  
Educational and defensive purposes only. Test only on systems you own or have written permission to test.

  

    
What is SQL Injection?
SQL Injection (SQLi) is a critical web application vulnerability that lets a malicious actor interfere with the queries an application sends to its database. It occurs when user-supplied input is not properly validated or sanitized, or is concatenated directly into a query string instead of being handled separately. This can allow an attacker to run arbitrary SQL commands against the backend database management system (DBMS).

    
How it occurs
SQLi typically appears in dynamic web forms such as login portals, search bars, and user profile lookups, where developers build queries with direct string concatenation or variable interpolation. In the example below, whatever the user types goes straight into the query text.

  

  

    

      Insecure
      
Vulnerable code (PHP/MySQL)


// Insecure: user input is directly concatenated into the query string
$username = $_POST['username'];
$password = $_POST['password'];

$query = "SELECT * FROM users WHERE username = '$username' AND password = '$password'";
$result = mysqli_query($conn, $query);

      
If an attacker enters ' OR '1'='1 in the username field, the query the database receives becomes:


SELECT * FROM users WHERE username = '' OR '1'='1' AND password = ''

      
The condition '1'='1' is always true, so the input changes the logic of the query instead of being treated as a value. Combined with how the rest of the query is handled, this can let an attacker bypass authentication without a valid password.

      
Accuracy note: in this exact string, AND is evaluated before OR, so on its own it would only match rows with an empty password. Real attacks usually neutralize the rest of the query as well. That is why the fix must remove the cause, not just block specific strings.

    

    

      Secure
      
Prepared statement with PDO


// Secure: prepared statement with a bound parameter
$stmt = $pdo->prepare('SELECT id, username, password_hash FROM users WHERE username = :username');
$stmt->execute(['username' => $_POST['username']]);
$user = $stmt->fetch();

if ($user && password_verify($_POST['password'], $user['password_hash'])) {
    // Authentication successful
}

      
The query structure is sent to the database first and the input is bound separately, so it is always treated as data and never as SQL. The password is checked with password_verify() against a stored hash instead of being placed inside the query.

Potential risks and consequences

  

    
Unauthorized data access
Attackers can bypass login controls, view confidential user records, extract personally identifiable information (PII), or reach financial data.

    
Data tampering and loss
Malicious queries can modify records, corrupt datasets, or drop entire tables with destructive commands such as DROP TABLE.

    
Privilege escalation
Attackers may gain administrative database privileges and interact with the underlying host operating system.

    
Regulatory violations
Breaches from unpatched vulnerabilities can bring legal penalties and non-compliance with data privacy frameworks such as GDPR.

  


  
Prevention techniques

  

    
Parameterized queries
The primary defense. Prepared statements make the database treat user input strictly as data, never as executable SQL.

    
Object-Relational Mapping (ORM)
Frameworks such as Entity Framework, Hibernate, and Eloquent parameterize queries through built-in abstraction layers. Raw queries inside an ORM still need parameters.

    
Input validation and sanitization
Apply strict whitelist validation, type checking, and length limits to all incoming parameters.

    
Principle of least privilege
Give the web application's database account only what it needs, such as SELECT, INSERT, and UPDATE on specific tables, and avoid rights like DROP or ALTER.

  


  
Recommended defensive measures

  

    
Web Application Firewall (WAF)
Monitor, filter, and block suspicious HTTP traffic patterns that point to SQL injection attempts.

    
Scanning and penetration testing
Run routine static (SAST) and dynamic (DAST) application security testing, plus manual code reviews.

    
Database auditing
Enable activity monitoring and logging to spot unusual query patterns or unauthorized access attempts in real time.
